# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Blockbuster is a personal desktop app (Tauri 2 + React 19 + TypeScript) for browsing and playing local movies. The user picks one library folder; the Rust backend scans it into a SQLite catalog that the Home and Movies (`/movies`) pages display. Clicking a movie plays it in mpv with saved and resumed progress. After each scan a background pass reads quality, duration and streams with ffprobe, stores OMDb details (plot, credits, ratings) and makes a thumbnail (OMDb poster, else an ffmpeg frame); a movie details page shows them offline. The MVP scope lives in [README.md](README.md). Read its "MVP goal", "Features", "Architecture" and "Out of scope" sections before adding features. Keep work inside the first-milestone scope: one library folder, local catalog, mpv playback, resume progress, posters, quality and stored movie details.

## Commands

- `npm run tauri dev`: run the desktop app. It starts Vite on port 1420 (`strictPort`, so it fails if the port is in use) and then `cargo run` in `src-tauri/`.
- `npm run tauri build`: build a release bundle (runs `npm run build` first, frontend output goes to `dist/`).
- `npm run build`: type-check (`tsc`) and build the frontend only.
- `cargo check` / `cargo test` from `src-tauri/`: backend-only checks. Run a single Rust test with `cargo test <test_name>` (e.g. `cargo test catalog`). `cargo clippy` needs the separate Fedora `clippy` package.

No JS test runner, linter or formatter is configured yet.

### Linux build prerequisites (Fedora)

The Rust build links against system GTK/WebKit libraries. If `glib-sys`, `gdk-sys` or similar fail with "pkg-config ... not found", install:

```bash
sudo dnf install webkit2gtk4.1-devel gtk3-devel glib2-devel openssl-devel \
  libappindicator-gtk3-devel librsvg2-devel libxdo-devel
```

Playback needs `mpv` on `PATH` (`sudo dnf install mpv`). Quality, durations and frame thumbnails need `ffmpeg` (which provides `ffprobe`). Posters need a free OMDb key: run `OMDB_API_KEY=<key> npm run tauri dev`; without it every movie gets a frame. Online subtitle search needs `OPENSUBTITLES_API_KEY` the same way; without it, subtitles still work from files. Run `cargo test -- --ignored` for the integration tests that drive real mpv and ffmpeg.

## Architecture

Diagrams of the components, the scan/metadata flow and playback: [docs/architecture.md](docs/architecture.md). Update them when those flows change.

- **Frontend** (`src/`): React app served by Vite. It calls the backend with `invoke("<command>", { args })` from `@tauri-apps/api/core`.
  - **Feature folders (required)**: all app code lives in `src/features/<feature>/`, split by role into `components/`, `hooks/`, `api/` (Tauri `invoke` wrappers and DTO mappers), `data/` (static config, mocks), `lib/` (pure helpers) and `types.ts`. Each feature exposes its public API through `index.ts`. Other features and routes import only from `@/features/<feature>`, never deep paths; files inside a feature use relative imports. Current features: `layout` (app shell: header and a sidebar that collapses to icons (`Ctrl+B` or its rail), with movie counts, quick views linking to filtered Movies, and a footer card for the library folder and disk usage), `theme` (provider, `useTheme`, toggle), `library` (shared catalog data, folder picker, movie grid and cards; kept media-neutral so a planned TV Shows tab can reuse it), `home`, `movies` (the `/movies` page: every catalog movie, filtered (search, watch status, quality, decade, genre), sorted, optionally grouped (A–Z, decade, quality, watch status, folder) into collapsible sections, shown as a poster grid or a list table; the title search is the app header's search box, which writes `q` to the Movies URL; all of it is applied client-side and kept in the URL through the route's `validateSearch: parseMovieFilters`; the Genre menu lists the genres present in the catalog, from OMDb's `Genre` field), `movie-details` (the `/movies/$movieId` page, linked from each card title; it combines the catalog row with `get_movie_details`, whose query key sits under `libraryKeys.movies` so catalog refetches refresh it; it renders `SubtitlesCard` with the embedded subtitle streams from `media_json`), `subtitles` (`SubtitlesCard`: a radio list of Automatic, Off, embedded, sidecar and added subtitles whose value is the remembered choice; add from file via the dialog plugin; `SearchSubtitlesDialog` for OpenSubtitles; adding or downloading one also selects it; `subtitleKeys` sit outside `libraryKeys.all`, and invalidations use `exact: true` so cached searches, which spend API requests, are not refetched). Shared helpers both features need (e.g. `languageLabel`) live in `library`.
  - **Outside features**: only shadcn-owned code (`src/components/ui`, `src/hooks`, `src/lib/utils.ts`, all written by `npx shadcn add` per `components.json`) and the entry point `src/main.tsx`, which mounts app-wide providers (`QueryClientProvider`, `ThemeProvider`, `TooltipProvider`, `Toaster`) above `RouterProvider`. Don't put app code in those shadcn folders.
  - **Server state**: backend data goes through TanStack Query. Query and mutation keys live next to the API wrappers (`libraryKeys` in `src/features/library/api/library-api.ts`); mutations invalidate `libraryKeys.all`, and every library mutation uses a key under that prefix so `useLibraryBusy()` can disable all scan/folder buttons together. Queries never go stale on their own (`staleTime: Infinity`), so anything that changes the catalog must invalidate. Command errors reject with a plain string; show them with `errorMessage()` and `toast.add(...)` from `@/components/ui/toast`.
  - **Remaining mock data**: the sidebar disk-usage card (`src/features/layout/data/mock-disk-usage.ts`). Home is a rotating billboard (the latest in-progress movie, then unwatched picks; slides are tracked by movie id so refetches don't swap them) and shelves built from real catalog data (continue watching, recently added, unwatched, 4K, the largest decade, watch again), each with a "View all" link to `/movies` with matching filters; random picks use `seededOrder`, seeded once per visit so rescans don't reshuffle. There is no watchlist or favorites (out of scope).
  - **Theme**: `index.html` has an inline pre-paint script that applies the `dark` class; its storage key must match `THEME_STORAGE_KEY` in `src/features/theme/lib/theme-storage.ts`.
  - **Routing**: TanStack Router, file-based. Route files in `src/routes/` stay thin: they only bind a path to a page component exported by a feature, passing route params and search state in as props so features never import route ids (`__root.tsx` wraps `<Outlet />` in `AppLayout`). The Vite plugin regenerates `src/routeTree.gen.ts` on dev/build; never edit it by hand.
  - **UI**: Tailwind v4 (configured in `src/index.css`, no `tailwind.config`) and shadcn/ui (`base-nova` style, Base UI primitives, lucide icons). Add components with `npx shadcn@latest add <name>`; they land in `src/components/ui/`. Base UI uses a `render` prop, not `asChild`. For nav links, style a router `Link` with `buttonVariants()`.
  - Import alias `@/` maps to `src/` (set in both `tsconfig.json` and `vite.config.ts`).
- **Backend** (`src-tauri/`): `main.rs` only calls `blockbuster_lib::run()`. All app logic belongs in the library crate (`src/lib.rs` and modules under it). New commands are `#[tauri::command]` functions that must be registered in `tauri::generate_handler![...]` in `lib.rs`; argument names in `invoke` must match the Rust parameter names (camelCase on the JS side maps to snake_case in Rust). Every command is `async` and does its work inside the `blocking()` helper in `src/library/commands.rs` (`spawn_blocking`), so neither the main thread nor async workers wait on the DB lock or the file system.
  - **Database** (`src/db.rs`): one `rusqlite` connection (bundled SQLite) in managed state as `Db(Mutex<Connection>)`, stored at `<app data dir>/blockbuster.db` (`~/.local/share/com.jintudas.blockbuster/` on Linux). Migrations are a `MIGRATIONS` array applied by `PRAGMA user_version`: only append, never edit a shipped entry.
  - **Library** (`src/library/`): `scanner.rs` walks the folder (videos only, hidden entries skipped, no symlinks), `title.rs` derives title and year from the file name (`RELEASE_TAGS` end a title, word-like `TRAILING_TAGS` are only trimmed from its end), `catalog.rs` diffs a scan against the `movies` table (insert, update, mark `missing`; rows are never deleted so progress survives; a size change means a different file and clears duration/quality/progress (the thumbnail stays), a modification-time-only change keeps them; movies at or under unreadable paths are left alone; rows from a previous library folder are hidden but not counted as missing), `commands.rs` exposes `get_library_folder`, `set_library_folder`, `scan_library`, `list_movies`, `get_movie_details`, `get_thumbnail`. `scan_library` and playback share `rescan_saved_folder`. Every scan emits `library-updated` when it changed anything, and refuses a scan that finds no files where the catalog has movies (`catalog::looks_unmounted`: an unmounted drive's empty mount point), so the library is never emptied by accident. The frontend rescans once at launch (`useStartupScan`, mounted in `AppLayout`), a normal scan mutation, so it shows as busy and toasts only on changes or errors. Scans hold `ScanLock` for their whole run, and the folder setting plus scan results are written in one transaction, so a failed scan never changes the saved folder. Each Rust module carries its own `#[cfg(test)]` tests; DB tests use `db::open_in_memory()`.
  - **Player** (`src/player/`, Unix only): `mpv.rs` launches mpv with an IPC socket in `$XDG_RUNTIME_DIR` (socket paths must stay under ~108 bytes, so never `TMPDIR`) and parses its JSON events; it overrides user config that breaks tracking (`keep-open`, `idle`, mpv's own resume). `session.rs` tracks one playback on a thread, saving every 10 s and on exit via `catalog::save_playback`; `progress_to_store` clears the position when watched past 95%, played to EOF or stopped under 10 s, and keeps it when no position was reported. When a session ends it emits the `playback-ended` event, which `useCatalogSync` (mounted in `AppLayout`) turns into a catalog refetch. `mpv.rs` also loads sidecars with `--sub-file` (mpv's own sidecar loading skips files already loaded, so the user's `sub-auto` config still applies) and passes Off as `--sid=no`; everything else waits for `track-list`, where `session::SubtitleSetup` adds the added subtitles over IPC (`sub-add … auto`, or `select` for the chosen one, so Automatic keeps mpv's pick) and selects an embedded choice (n-th non-external sub track; too few keeps mpv's pick) or a sidecar by its real track id. No track number is ever guessed. `commands.rs` exposes `play_movie(movie_id, from_start)`. When the file is not found it rescans the folder under `ScanLock` instead of hiding the movie itself, then says whether the movie was removed or its drive may be unmounted (other read errors leave the catalog alone); one movie plays at a time (`Player` state), and `lib.rs` stops mpv on `RunEvent::Exit` so the position is saved when the app closes.
  - **Subtitles** (`src/subtitles/`): `sidecar.rs` lists files next to the video named after it (`Movie.en.forced.srt`; read live, never stored) and guesses languages from name tokens; `store.rs` keeps added subtitles (`subtitles` table, files at `<app data>/subtitles/<id>.<ext>`) and the per-movie `subtitle_choice` (`off`, `embedded:<n>`, `sidecar:<name>`, `added:<id>`; `NULL` lets mpv decide), and builds the `SubtitlePlan` for playback from sidecars the caller read before taking the DB lock, falling back to Automatic when the chosen file is gone; multi-statement writes run in one transaction; `opensubtitles.rs` is the OpenSubtitles REST client (`OPENSUBTITLES_API_KEY`; search by IMDb id from `omdb_json`, else title and year, ranked by movie-hash match then downloads; parameters sent alphabetically). `commands.rs` exposes `list_subtitles`, `set_subtitle_choice`, `add_subtitle_file` (srt/ass/ssa/vtt/sub up to 5 MB), `remove_subtitle`, `search_subtitles`, `download_subtitle` (a file already downloaded for the movie is reused, not downloaded again; a lock makes check, download and store one step). A sidecar belongs to the video with the longest matching name, so `Movie.Extended.en.srt` is never `Movie.mkv`'s.
  - **Media** (`src/media/`): `probe.rs` runs ffprobe for a quality label (width counts as much as height, so cropped encodes stay 1080p/4K; `HDR` for PQ/HLG) and duration. `poster.rs` looks up OMDb by title and year and downloads the poster, or grabs an ffmpeg frame 10% in. `enrich.rs` runs one background pass at startup and after every scan (a scan during a pass queues one rerun): it handles rows where `probed_size_bytes IS NOT size_bytes`, `thumbnail_file IS NULL` (unless `frame_failed_size` matches the file), or (with a key) `poster_lookup = 0` or `details_lookup = 0` (never-looked-up movies first, so a catch-up can't spend the daily OMDb quota before new movies), holds the DB lock only for each write, and emits `library-updated` at most every 3 s, which `useCatalogSync` also refetches on. The pass also stores OMDb's raw reply (`omdb_json`, fetched with `plot=full`; a year-less unique search hit is looked up again by IMDb id) and ffprobe's stream list (`media_json`, `probe::MediaInfo`); a size change clears `media_json` but keeps `omdb_json`. `details_lookup` marks that a lookup storing the reply has run (migration v5 re-queues every movie without a stored reply once); a re-lookup always downloads the poster again so it matches the stored reply. `get_movie_details(movie_id)` returns both as JSON text, plus whether OMDb has answered and whether a key is set, so the page can say why details are missing; `list_movies` leaves them out to stay small, except OMDb's `Genre`, which it reads from `omdb_json` with `json_extract` for the Movies genre filter. Only failures that would hit every movie (ffprobe/ffmpeg not installed, network down, bad key, rate limit) skip a tool for the rest of the pass without marking rows done; per-title outcomes (OMDb miss, dead poster link, no frame) are recorded so they are not retried. Unopenable files are skipped, not recorded. A per-movie error is logged and the pass continues. Without a year, a poster is taken only from a single same-title search hit. Thumbnails whose file was deleted are forgotten and remade (`forget_thumbnail`). Thumbnails are `<app data>/thumbnails/<id>-poster.jpg` or `<id>-frame.jpg`. The webview loads them with the `get_thumbnail(movie_id)` command (raw bytes, turned into a data URL by `useThumbnail`; movie cards only load it once they come near the viewport, via `useInView`), not the asset protocol: WebKitGTK blocks `asset://` images on a page served from `http://localhost:1420`.
  - Media files are read-only; generated data (DB, thumbnails) goes in the app data directory.
- **Permissions**: Tauri 2 denies plugin APIs by default. Adding a plugin means adding it in `Cargo.toml`, calling `.plugin(...)` in `lib.rs`, installing the JS package, and granting its permissions in `src-tauri/capabilities/default.json` (currently `dialog:allow-open` for the folder picker).
- `src-tauri/gen/` is generated by the Tauri build; do not edit it by hand.
